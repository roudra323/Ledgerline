# Ledgerline — Failure Modes

> This document is the point of the project. A payment rail is defined by what it does when things
> go wrong, not by its happy path.

Every entry below follows the same shape: **trigger → detection → designed response → the test that
proves it.** An entry with no test is a claim, not a design; entries still awaiting their test are
marked `TODO(Phase N)`.

Three rules govern everything here:

1. **Nothing is credited on a hint.** A receipt, a 200 response, or an optimistic local write are
   hints. Only a durably-recorded fact from an external source of truth moves a saga.
2. **Compensations are ordered so the recoverable failure happens last.** See
   [ADR-0008](decisions/0008-compensation-ordering.md).
3. **Where no compensation exists, say so.** Some failures resolve to a debt entry and a human. That
   is a designed outcome, not a gap.

## A. Fiat rail

| #       | Failure                                                | Detection                                                                            | Designed response                                                                                                                                                                                                                                                                                                                                      | Test                                                                                      |
| ------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------- |
| **A1**  | Duplicate webhook (same `provider_event_id`)           | `UNIQUE(provider, provider_event_id)`                                                | `INSERT ... ON CONFLICT DO NOTHING`. Even a double _dispatch_ is a no-op because `saga_transitions` is uniquely keyed by cause. **Two independent layers.**                                                                                                                                                                                            | Fire the same payload 50× concurrently → exactly one ledger transaction                   |
| **A2**  | Webhook arrives before our own DB write commits        | The dispatcher finds no matching aggregate                                           | Persist to `fiat_events`, return **200**, mark `unmatched`, retry with backoff. The intent row is also created _before_ we call the PSP, so the window is tiny. **Never return 4xx/5xx to force a PSP retry** — that hides the problem behind their retry policy and produces duplicate storms. Alert `UnmatchedFiatEventAging` after 15 min.          | Deliver a webhook for an intent that does not exist yet, then create it → saga completes  |
| **A3**  | Out-of-order: refund event before capture event        | Transition classifier returns `DEFER`                                                | Row → `deferred`, `next_attempt_at = now() + backoff`. If the capture never arrives, the poller (A5) fetches it. Alert after N deferrals.                                                                                                                                                                                                              | Deliver refund then capture → same terminal state as capture-then-refund                  |
| **A4**  | Capture arrives _after_ we timed out the authorization | Classifier returns `ILLEGAL` for `capture_failed → captured`                         | Dead-letter **and page**: we told a customer "declined" and then took their money. Automatic compensating refund saga.                                                                                                                                                                                                                                 | Assert `ILLEGAL` classification, the alert, and the auto-refund                           |
| **A5**  | PSP says succeeded; we never got the webhook           | `PspReconciler`, hourly, over non-terminal intents older than T                      | Poll the PSP and synthesize a `fiat_events` row with `provider_event_id = 'poll:<object>:<status>'`. A later real webhook still collapses to the same logical transition via `saga_transitions`. Metric `ledgerline_psp_poll_recovered_total`. Backstop: the daily settlement file.                                                                    | Drop the webhook via the fault API → poller recovers → one ledger transaction             |
| **A6**  | Forged webhook                                         | HMAC-SHA256 over the **raw body**, `crypto.timingSafeEqual`, timestamp within ±5 min | Reject 400, `ledgerline_webhook_signature_failures_total`, alert `ForgedFiatEvent` at any sustained rate. **There is no benign explanation** — this is a security incident, not a reconciliation one.                                                                                                                                                  | Tampered body and wrong-secret signature both rejected; constant-time comparison asserted |
| **A7**  | Replayed webhook with a valid old signature            | Timestamp window + `provider_event_id` unique                                        | Outside 5 min → rejected on the window. Inside → rejected on the unique key.                                                                                                                                                                                                                                                                           | Replay a captured payload at T+10min                                                      |
| **A8**  | Clock skew between us and the PSP                      | `ledgerline_psp_clock_skew_seconds` from `provider_created_at - received_at`         | Provider timestamps are used **only** for the HMAC replay window and for display. **Ordering is never derived from timestamps** — it comes from state-machine legality. | **A9**  | PSP captured a different amount than quoted            | Compare `captured_amount_minor` against the snapshot                                 | **The PSP's number is authoritative.** Recompute the token amount from the actual capture. | **A10** | Duplicate idempotency key with a **different** body    | `idempotency_keys.request_hash`                                                      | Same key + same hash + `completed` → replay the stored response. Same key + same hash + `in_flight` → `409` + `Retry-After`. Same key + **different** hash → `422 IdempotencyKeyReuse`, never processed.                                                                                                                                               | All three branches asserted explicitly                                                    |
| **A11** | Idempotency key reused across merchants                | Scope is `(merchant_id, key)` in both the PK and `payment_intents`                   | Two merchants may use the same key string independently.                                                                                                                                                                                                                                                                                               | Two merchants, same key → two intents                                                     |
| **A12** | Chargeback after we already paid out                   | Late `fe:chargeback` on a settled intent                                             | Irreversible on **both** legs. `DR chargeback_loss / CR bank_settlement` (the money left) plus `DR merchant_receivable:M / CR chargeback_loss` (we now hold a claim). `merchants.is_payouts_frozen = true`; future payouts net against the receivable. Metric `ledgerline_merchant_debt_minor`. **Compensation here is a business process, not code.** | Chargeback-after-payout produces the debt entry and freezes payouts                       |
| **A13** | Refund required but the refund window expired          | Guard in `refunds.validate`                                                          | `refunding → manual_review`, opening a `merchant_receivable`. Never silently dropped.                                                                                                                                                                                                                                                                  | Refund past the window → `manual_review`, not `rejected`                                  |
| **A14** | PSP outage / 5xx on capture                            | Outbox attempt failure                                                               | Exponential backoff, **reusing the same `Idempotency-Key`** (the outbox `dedupe_key`), so a retried capture can never double-charge. After `max_attempts` → `dead` + `capture_failed` + alert.                                                                                                                                                         | Fail the PSP for N attempts → exactly one charge                                          |
| **A15** | PSP times out — did the charge happen?                 | No response at all                                                                   | **Never assume.** Poll by our own idempotency key on the next tick. This is precisely why the key is derived from our aggregate id and not random.                                                                                                                                                                                                     | Timeout injection → recovered by poll, one charge                                         |
| **A16** | ACH/SEPA payout returned days later (R-code)           | Late `fe:payout.returned`                                                            | Modelled explicitly: `fiat_settled → returned`; `DR bank_settlement / CR merchant_fiat_payable` re-opens the obligation. **"Settled" is not "final" on the fiat rail either** — fiat has its own reorg; it is just slower and called a return.                                                                                                         | Late-return fault → obligation re-opened, balances correct                                |

## B. Chain write path

| #       | Failure                                                                           | Detection                                                                                   | Designed response                                                                                                                                                                                                                                                                                                                                                                                  | Test                                                                            |
| ------- | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| **B1**  | Chain tx succeeds but we crash before recording it                                | —                                                                                           | **Structurally impossible**: the signed `raw_tx` + `intent_key` commit _before_ broadcast. On restart: re-broadcast every non-confirmed attempt (`already known` / `nonce too low` are **success** signals), poll receipts for every attempt hash, and compare `eth_getTransactionCount(latest)` against our max assigned nonce to detect anything landed-but-unmapped.                            | Crash-injection matrix, 6–8 points → exactly one mined tx per intent            |
| **B2**  | Card captured but the chain tx reverts                                            | `receipt.status = 0`; decode by re-running `eth_call` at `mined_block − 1`                  | Branch on the **decoded custom error**: `ContractPaused` → retry, do not refund. `AccountBlacklisted` → `frozen` + `manual_review`, do **not** auto-refund (we may be prohibited from returning the funds). `PaymentAlreadySettled` → we already paid; jump the saga forward. Only genuine non-transient failures refund.                                                                          | One test per revert reason → correct branch                                     |
| **B3**  | Nonce gap (N never mined; N+1…N+k stuck behind it)                                | `MIN(nonce) WHERE status='submitted'` unchanged past `STUCK_AFTER` while later nonces exist | Escalate **only the oldest**. Bumping a later transaction cannot help — it is unminable behind the hole — and burns fees. `ledgerline_chain_nonce_gap_depth`, `NonceGap` alert.                                                                                                                                                                                                                    | Force a hole → assert only `MIN(nonce)` is re-signed                            |
| **B4**  | Stuck at the fee ceiling                                                          | `maxFeePerGas` at `MAX_FEE_CEILING_WEI`                                                     | Stop escalating. `StuckTransaction` critical + operator cancel endpoint (same nonce, `to = self`, value 0, aggressive fees). The saga stays in `chain_submitted` — **correct, because we genuinely do not know** — and the merchant-facing API says `processing`, never `failed`.                                                                                                                  | Ceiling reached → no further attempts, alert fires, cancel resolves             |
| **B5**  | Nonce desync (Anvil restart, or a manual tx from our key)                         | `nonce too low` on a fresh submission                                                       | Resync `next_nonce = max(eth_getTransactionCount(latest), max assigned + 1)`. A `nonce too low` on a _fresh_ submission means someone else used our key → route to B21.                                                                                                                                                                                                                            | Manual out-of-band tx → resync, no duplicate                                    |
| **B6**  | Anvil wiped but Postgres persisted (the daily dev reality)                        | `chain_fingerprint` genesis-hash mismatch at boot                                           | **Refuse to start**, with a clear message and a `make reset` hint. Saves hours of phantom-drift debugging.                                                                                                                                                                                                                                                                                         | Swap the genesis → boot fails with the expected message                         |
| **B7**  | Reorg re-includes our tx at a different block or `log_index`                      | Parent-hash continuity check                                                                | The partial unique index ([ADR-0010](decisions/0010-raw-events-partial-unique.md)) lets the orphaned copy and the canonical copy coexist. Confirmation math reads only non-orphaned rows.                                                                                                                                                                                                          | `anvil_revert` + re-mine at a different index → both rows present, math correct |
| **B8**  | Reorg **within** confirmation depth, after we credited                            | Reorg guard orphans the events                                                              | Compensating `saga_transitions` + **reversing** `ledger_transactions` (`reverses_id`), never deletes. The chain tx returns to `submitted` and replays naturally. **Self-healing.**                                                                                                                                                                                                                 | Reorg within depth → ledger nets to the same place via reversals                |
| **B9**  | Reorg **deeper** than `confirmations_required`, after an irreversible fiat payout | Depth exceeds policy                                                                        | **Cannot be healed.** Reversing entries + `manual_review` + `ReorgBeyondConfirmations` (page) + global payout freeze until an operator clears it. This is why confirmation depth is a _risk budget_ and why payout depth is 2× settle depth.                                                                                                                                                       | Deep reorg → `manual_review`, alert, payouts frozen                             |
| **B10** | The RPC lies about a receipt                                                      | Three defences                                                                              | (1) Never trust a receipt's `blockHash` alone — re-fetch the block **by number** and compare. (2) Require `confirmations_required` depth. (3) **Before any irreversible fiat action**, cross-check the confirming block hash against the second provider. Disagreement → `RpcDisagreement` critical + hold the payout. _This is what earns `anvil2` its place in compose._                         | Divergent second provider → payout held, alert fires                            |
| **B11** | RPC returns `null` receipt for a tx we know is mined                              | Provider indexing lag                                                                       | Treat `null` as **unknown**, never as "not mined." Only absence at `head − depth` on _both_ providers is evidence of non-inclusion.                                                                                                                                                                                                                                                                | Null-receipt injection → no premature failure                                   |
| **B12** | Treasury runs out of gas                                                          | `ledgerline_chain_account_balance_wei{role}` below watermark                                | Auto-refill outbox job from `gas_funder`. Below the hard floor the submitter **circuit-breaks**: sagas park in `awaiting_gas` rather than burning retries into the dead-letter. **Parking beats failing.**                                                                                                                                                                                         | Drain gas → sagas park, refill → they resume                                    |
| **B13** | Treasury runs out of stablecoin float (off-ramp)                                  | `liquidity_positions` min/target/max                                                        | The reservation into `token_in_transit` is taken **under the account row lock before submission**, so concurrent sagas cannot both spend the same float. Insufficient → `awaiting_liquidity` + `FloatBelowMinimum`. _On the on-ramp we are the issuer, so float is elastic — that is a property of being the issuer, not a general truth, which is exactly why the off-ramp needs this machinery._ | 20 concurrent payouts against float for 10 → exactly 10 succeed, 10 park        |
| **B14** | Minter allowance exhausted                                                        | Pre-flight simulation returns `ExceedsMinterAllowance`                                      | Park in `awaiting_liquidity`; `MinterAllowanceLow` at 20% remaining. **Deliberately not auto-topped-up** — a minter allowance is a safety limit, and auto-raising it defeats the control.                                                                                                                                                                                                          | Exhaust the allowance → park, no nonce consumed                                 |
| **B15** | Token paused mid-payout                                                           | Simulation catches most; mid-flight → `rcpt:reverted(TokenPaused)`                          | `blocked_paused`, resumed by the indexed `Unpause` event. **No fiat compensation** — a pause is transient by design.                                                                                                                                                                                                                                                                               | Pause mid-flight → blocked → unpause → resumes                                  |
| **B16** | Recipient blacklisted between quote and settlement                                | Simulation, then `AccountBlacklisted` revert                                                | `frozen`; ledger moves `merchant_payable → frozen_payable`. Funds stay in treasury. **The fiat is not auto-refunded** — we may be legally required to hold it. `manual_review`. _The case where "correct engineering" and "just reverse it" diverge._                                                                                                                                              | Blacklist mid-flight → `frozen_payable`, no auto-refund                         |
| **B17** | Merchant changed their settlement address mid-flight                              | —                                                                                           | `destination_address` is snapshotted on the intent at creation and never re-read (as are `fee_bps_snapshot` and the FX rate). **A config change must never retroactively alter an in-flight payment.**                                                                                                                                                                                             | Change the address after quote → funds go to the snapshotted address            |
| **B18** | Two submitters race on the same intent                                            | `UNIQUE(intent_key)` + `chain_accounts` row lock + `pg_advisory_lock`                       | Three off-chain guards; and even if all three failed, `PaymentAlreadySettled` on-chain makes the second a revert rather than a double payment.                                                                                                                                                                                                                                                     | Two concurrent submitters → one mined tx                                        |
| **B19** | Double-spend of the same EIP-3009 authorization                                   | `authorizationState` is one-shot on-chain                                                   | Impossible on-chain. Off-chain rule: **an authorization is never treated as money until its event confirms.** A second submission reverts `AuthorizationAlreadyUsed` → look up the existing event and reconcile _forward_, do not fail.                                                                                                                                                            | Submit the same authorization twice → one settlement                            |
| **B20** | EIP-3009 authorization expires before we mine                                     | `validBefore` = `quote_expires_at`                                                          | One deadline, one concept: an expired authorization and an expired quote fail together. Revert `AuthorizationExpired` → `expired`, request a new signature.                                                                                                                                                                                                                                        | Expire mid-flight → `expired`, clean retry                                      |
| **B21** | **Unknown outflow from the treasury** (key compromise)                            | Invariant **I8**, checked inside the `Transfer` handler                                     | Any `Transfer` with `from = treasury` and no matching `chain_transactions` row → set `chain_accounts.is_frozen`, halt the submitter, **page**. **The single highest-severity alert in the system.** The runbook says: assume key compromise until proven otherwise; freeze first, investigate second.                                                                                              | Out-of-band treasury transfer → frozen + paged                                  |
| **B22** | `block.timestamp` used for a business deadline                                    | Code review + lint                                                                          | **Banned.** Block timestamps are miner-influenced and, on Anvil, arbitrary. Deadlines come from Postgres `now()`. Block timestamps are display-only. EIP-3009's `validBefore` is the one legitimate exception — it is the _contract's_ deadline and deliberately loose.                                                                                                                            | — (convention, enforced in review)                                              |

## D. Cross-cutting

| #      | Failure                                                              | Detection                                                             | Designed response                                                                                                                                                                                                                                                                                                                          | Test                                                        |
| ------ | -------------------------------------------------------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------- |
| **D1** | Outbox consumer crashes after the side effect, before marking `done` | Lease expiry                                                          | At-least-once delivery; the message is redelivered. Every consumer **must** be idempotent, and the mechanism is that the outbox `dedupe_key` **is** the downstream idempotency key (PSP `Idempotency-Key`, `chain_transactions.intent_key`). This is a structural requirement enforced by the `OutboxHandler` interface, not a convention. | Kill after the side effect → redelivery is a no-op          |
| **D2** | Poison message loops forever                                         | `attempt > max_attempts`                                              | → `dead` + `OutboxDeadLetter` alert + an admin requeue endpoint.                                                                                                                                                                                                                                                                           | Always-failing handler → dead after N, alert fires          |
| **D3** | Screening list updated between capture and payout                    | —                                                                     | Screening is **re-run at the payout gate**, never reused from capture. `screening_checks` stores `list_version` + `list_sha256`, so a past decision is explainable and replayable against the list _as it was_.                                                                                                                            | Address added to the list after capture → payout blocked    |
| **D4** | Screening vendor is down                                             | Adapter timeout / error                                               | **Fail closed.** Park in `screening_pending` and retry. Never credit or pay out on an unavailable screening result — deliberately the opposite of the usual "fail open for availability" instinct, because the cost of a wrong _allow_ is unbounded and the cost of a delay is not.                                                        | Vendor down → parked, never credited                        |
| **D5** | Velocity limit race (two payments each under the cap, together over) | `limit_counters` row-locked in the same transaction as the transition | Serialized.                                                                                                                                                                                                                                                                                                                                | Two concurrent at 60% of cap → one succeeds                 |
| **D6** | Replay corrupts history                                              | —                                                                     | `ReplayService` rebuilds **projections only**. It runs in a transaction with `UPDATE`/`DELETE` revoked on `raw_events`, `fiat_events`, `ledger_entries` and `saga_transitions`, so a bug in replay _cannot_ rewrite the logs.                                                                                                              | Replay with an intentionally buggy handler → logs unchanged |
| **D7** | Two indexer replicas both ingest                                     | Advisory lock per sync key                                            | Out of scope as a feature (inherited non-goal), but the lock makes it **safe-by-crash rather than safe-by-luck**. Stated as a non-goal, not left implicit.                                                                                                                                                                                 | —                                                           |
| **D8** | A migration needs to retire a status value                           | —                                                                     | Statuses are `text` + `CHECK`, **not** PG enums. Enum value removal is a migration nightmare, and historical `saga_transitions` rows must retain retired status names.                                                                                                                                                                     | Migration round-trip test                                   |

## Irreversibility map

The short version of everything above. These are the points past which no code can help.

| Transition                                             | Reversible?                                   | Compensation when not                                                                                                                      |
| ------------------------------------------------------ | --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `authorized → captured`                                | Yes, within the refund window                 | PSP refund + ledger reversal                                                                                                               |
| `captured → chain_submitted` (mint)                    | **Only before mining**                        | Burn from treasury if the tokens never left; otherwise `manual_review`                                                                     |
| Token delivered to a non-custodial merchant            | **No**                                        | No on-chain compensation exists. An off-chain **claim**: `merchant_receivable` + payout freeze + netting against future payouts            |
| `burn_confirmed` (off-ramp)                            | **No**                                        | Not "re-mint" — that changes the reserve math. `merchant_fiat_payable` stays open; re-mint only via an operator command under dual control |
| Fiat payout settled                                    | Only by the counterparty (an ACH return, A16) | Re-open the obligation                                                                                                                     |
| `settled` after a reorg deeper than confirmation depth | **No**                                        | `manual_review` + page (B9)                                                                                                                |

**Design rule that falls out of this table:** everything reversible — screening, limits, float checks,
simulation — happens **strictly before** the first irreversible step in each saga. That ordering is
not an optimization; it is the only lever available.
